# Spec: Cap PFactory's DB connection pools

## Design

New dependency-free module `apps/web-server/server/db_pool.py` with
`pool_kwargs(url, prefix, size, overflow) -> dict`. For a non-SQLite URL it
returns `pool_size` / `max_overflow` from `<prefix>_POOL_SIZE` /
`<prefix>_MAX_OVERFLOW` (defaults given by the caller) and `pool_timeout` from
`DB_POOL_TIMEOUT` (default 10 s). For SQLite it returns `{}` so local dev keeps
SQLAlchemy's SQLite pool choice. A non-integer env value raises at startup.

| Engine | Env prefix | Default | Before |
| --- | --- | --- | --- |
| main (`server/database/engine.py`) | `DB` | 5 + 3 = 8 | 15 |
| JobStateStore (`server/jobstore/store.py`) | `JOBSTORE_DB` | 2 + 2 = 4 | 10 |
| PlanSessionStore (`server/jobstore/plan_session_store.py`) | `PLAN_SESSION_DB` | 2 + 2 = 4 | 10 |
| WS relay (`server/websockets/relay.py`) | unchanged | 2 + 1 LISTEN = 3 | 3 |

Per pod 38 → 19; at 4 pods 152 → 76, leaving 21 of 97. The module sits
outside `server.database` because importing that package builds the main engine.

## Alternatives rejected

- Raise Postgres `max_connections` in factory-gitops: out of scope for this
  lane (no gitops change) and only moves the ceiling.
- PgBouncer: new infrastructure for a sizing problem.
- One shared engine for all three: the stores run on their own event loops
  (asyncpg binds connections to the creating loop), so they cannot share.

## Risks

- Too-small pools under bursty load give fast `TimeoutError`s instead of
  waits; mitigated by env overrides and by measured use of 3/pod.
- AIFactory/TFactory remain at defaults (reported in the PR, not changed).

## Verification

- Unit test of `pool_kwargs` (defaults, env override, SQLite → `{}`).
- Test that the stores' engines report the capped pool size.
- Full web-server backend suite, including against a local Postgres.

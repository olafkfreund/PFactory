# Spec: relay WebSocket events between pods through Postgres

## Two corrections to the approved intent

**1. Decision 1 (notify a pointer) cannot work, and is not needed.**

The premise was that log content is already persisted and a receiving pod could
read it. It is persisted — `TaskLogWriter` writes `task_logs.json` — but on the
*emitting pod's* filesystem, and `charts/pfactory/values.yaml:330-347` states the
volume is `ReadWriteOnce`, "fine for the v1.0 single-replica web-server… the
workspace PVC will then need to be RWX for cross-pod access". Pod B cannot read
pod A's file, so a pointer is unreadable.

It is also unnecessary: `emit_task_logs_stream` (`events.py:292`) already goes
through `broadcast_event`, so the task-detail log stream is fixed by relaying the
send functions, carrying one chunk per notification. Oversized payloads are
handled by a **size guard** (below) rather than a pointer.

**2. A stale note in the chart names a different mechanism.** The same comment
promises "v1.1's Redis-fan-out (#40)". `#40` in this repo is an unrelated closed
issue, so the reference is stale — but the documented intent was Redis, whereas
approved decision 3 says Postgres directly. This spec follows the approved
decision (no new dependency) and rewrites the stale comment. **Flagged for
review**: if Redis is genuinely wanted, say so now — it changes the transport, not
the seams.

## Design

### The seam

One relay module, `server/websockets/relay.py`, with two halves:

    async def publish(kind: str, payload: dict) -> None   # emitting pod
    async def start_listener(deliver) -> None             # every pod

Every pod publishes on channel `pfactory_ws`, and every pod listens. `payload`
carries `{"origin": <pod id>, "kind": ..., "data": {...}}` where the pod id is
`HOSTNAME` (the pod name under Kubernetes) plus a process-start nonce, so a
listener can skip its own notifications.

### Delivery order (approved decision 2)

Each send function delivers to its **local** sockets first, exactly as today, then
publishes. A relay failure is logged and swallowed: a DB hiccup must not silence
a browser attached to the emitting pod, which is the only behaviour that exists
in production now. The listener, on receiving a notification whose `origin` is not
this pod, calls the same local delivery function.

Consequence, stated plainly: ordering is per-pod, not global. Two events emitted
on different pods can arrive in either order at a third pod. Every payload
already carries a timestamp, and the existing sequence numbers
(`_get_next_sequence_number`) are per task, so per-task order is preserved by the
emitter; cross-task order was never guaranteed.

### Wrapped functions

- `events.py`: `broadcast_event`, `send_to_user`, `send_to_org` — the three that
  walk a registry. The 63 call sites and every `emit_task_*` helper sit above
  them and change nothing.
- `logs.py` / `progress.py`: their `AgentService` callbacks fire only on the pod
  running the task, so `_emit_log` and `_emit_progress`
  (`services/agent_service.py:110`, and the callers in
  `agent_process_monitor.py`) publish as well, and the listener feeds the local
  callback registries.

### Size guard

Postgres caps a `NOTIFY` payload at 8000 bytes. `publish` measures the encoded
payload; over the limit it truncates `data.content` (or `data.chunk.content`) and
sets `"truncated": true`, which the client already tolerates for log chunks. A
payload that cannot be brought under the cap is dropped with a warning rather
than raising — a lost log line must not break a task.

### Connection

`LISTEN` needs a dedicated connection, so the listener opens its own `asyncpg`
connection from `DATABASE_URL` (converted from the SQLAlchemy URL), outside the
request pool. It runs as one task started in `server/main.py`'s lifespan and
cancelled on shutdown, reconnecting with backoff on connection loss. With
`DATABASE_URL` unset the relay is inert and every function is a no-op, so the
single-process and test paths behave exactly as they do today.

## Alternatives rejected

- **Redis pub/sub.** A new runtime dependency and a new failure domain for
  something Postgres already does. Only the stale chart comment argues for it.
- **Cookie/session affinity on the ingress.** Keeps one browser on one pod; does
  nothing for an event that *originates* on another pod. The issue says so.
- **Publish-then-deliver everywhere** (one path, global ordering). Rejected by
  approved decision 2: it makes local delivery depend on the DB.
- **Relaying at the 63 call sites.** Sixty-three chances to forget one.
- **A transport interface with one implementation.** Approved decision 3.
- **Sharing `task_logs.json` across pods** (RWX storage). A storage change, out
  of scope here, and it does not help the socket that never receives the event.

## Risks

- **Double delivery** if the origin check fails (e.g. two pods with the same
  `HOSTNAME`). The nonce makes a collision require the same pod name *and* the
  same process start, which is why it is there.
- **Notification loss** is silent by design: Postgres drops notifications for a
  listener that falls behind, and there is no replay. The portal's views already
  reconcile by polling REST, so a missed event degrades to the pre-WebSocket
  experience rather than corrupting state.
- **The relay does not make the portal fully correct with 2 replicas.** Task
  detail reads `task_logs.json` from the pod serving the request, and the volume
  is RWO. This lifts the WebSocket half of the pin only; #805, #828 and the
  storage question remain. Worth its own issue rather than silence.
- **A busy log stream on many pods** multiplies notifications by pod count. At
  the current scale (single-digit replicas) that is far below Postgres's
  capacity; if it ever matters, the fix is a per-task channel, not a new broker.

## Verification

1. Unit: `publish` is a no-op without `DATABASE_URL`; a notification whose
   `origin` matches this pod is not delivered twice; one whose origin differs is
   delivered locally.
2. Unit: the size guard truncates an oversized chunk, marks it, and drops a
   payload that cannot fit — asserting on the *delivered* payload, not on the
   call.
3. Integration, against the Dockerised Postgres used for #798's store tests: two
   relay instances on one database; publish from A; assert B's deliver function
   receives it and A's does not receive it twice.
4. Negative control: disable the origin check ⇒ the double-delivery test fails;
   stub `publish` to raise ⇒ local delivery still happens (the DB-hiccup
   constraint).
5. `tests/` suite plus the three gates run as CI runs them (see the `plan/` for
   #798 for the exact commands).

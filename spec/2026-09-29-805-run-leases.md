# Spec: running work is visible, guarded and stoppable from any replica

Decisions carried from the approved intent:

1. All four services (agent tasks, insights, changelog, PR review) use one
   shared lease helper.
2. A stop reaches the owning pod through a `stop_requested` flag on the lease
   row, which the owner polls on its heartbeat.
3. The lease TTL is 60 s and the heartbeat 15 s, both configurable.

## Design

### The table: `run_leases` (one migration, `down_revision` = current head)

| column | type | note |
|---|---|---|
| `kind` | `String(32)` | `task`, `insights`, `changelog`, `pr_review` |
| `key` | `String(255)` | the service's existing key (`project_id:spec_id`, `project_id`, `project_id:pr`) |
| `owner` | `String(128)` | `f"{socket.gethostname()}:{os.getpid()}"`: the pod, and the process within it |
| `lease_until` | `DateTime(timezone=True)` | on the database clock |
| `stop_requested` | `Boolean`, default false | set by a non-owner stop |

- The primary key is `(kind, key)`, so there is at most one lease per run
  key, across all pods.
- Rows live only while a run does; release deletes them.

### The helper: `server/services/run_leases.py`

Everything is async, uses the web-server `async_session_factory`, and gets
its times from the database (the #758 `_now_and_until` expression: `now()`
on Postgres, `datetime('now')` on SQLite).

- **`acquire(kind, key, *, steal=False) -> bool`:** `INSERT ... ON CONFLICT
  (kind, key) DO UPDATE SET owner, lease_until, stop_requested=false WHERE
  run_leases.lease_until < now() RETURNING owner`.
  - With `steal=True`, the `WHERE` is dropped.
  - True when this owner now holds the lease: a free key, an expired lease,
    or a steal.
- **`release(kind, key)`:** `DELETE ... WHERE kind, key AND owner = me`. A
  lease someone else took is never released by the old owner.
- **`is_active(kind, key) -> bool`** and **`active_keys(kind) -> list[str]`:**
  rows with `lease_until > now()`. Expired rows count as not running.
- **`request_stop(kind, key) -> bool`:** `UPDATE SET stop_requested = true
  WHERE kind, key AND lease_until > now() RETURNING owner`.
- **`stop_and_wait(kind, key, timeout)`:** `request_stop`, then poll
  `is_active` every second until it is false or `timeout` (default: heartbeat
  + 5 s) passes. Returns whether the lease is free.
- **`watch(kind, key, *, alive, stop)`:** spawns (via the existing
  `background.tasks.spawn`) one loop per run, which ticks every 1 s:
  - When `alive()` is false (the service's local dict no longer has the key:
    normal exit, failure, local stop or monitor cleanup), `release`, then
    return. This covers every existing removal site and the failover
    respawns (which keep the key) without touching them.
  - Every heartbeat (15 s), `UPDATE SET lease_until = now()+ttl WHERE kind,
    key AND owner = me RETURNING stop_requested`:
    - no row: the lease was lost (stolen or expired). Log WARNING, `await
      stop()`, return;
    - `stop_requested`: log INFO, `await stop()`, then keep ticking until
      `alive()` goes false and release;
    - a database error: log ERROR, keep running, and retry on the next
      heartbeat. A DB outage must not kill work. If it outlasts the TTL,
      another pod may start a duplicate, and the ERROR says so. That is the
      fail-safe the intent asks for: never silent.
- **Configuration:** `PFACTORY_RUN_LEASE_TTL_SECONDS` (default 60) and
  `PFACTORY_RUN_LEASE_HEARTBEAT_SECONDS` (default 15). An invalid or
  non-positive value means the default. The heartbeat is capped at TTL / 3.

### The services

Each keeps its local dict, which is still how it holds the process or task.
The lease is added around it.

| Service | Before registering the run | After registering | `stop` callback | Local key test (`alive`) |
|---|---|---|---|---|
| Agent tasks (`start_spec_creation` :694, `start_task_execution` :1041) | `acquire("task", task_id)`; False → raise the existing "already running" `ValueError` | `watch(...)` | `self.stop_task(task_id)` | `task_id in self.running_tasks` |
| PR review (`start_review` :286) | `acquire("pr_review", key)`; False → the existing already-running error | `watch(...)` | `self.cancel_review(project_id, pr)` | `key in self.running_reviews` |
| Changelog (`generate` :232) | `acquire("changelog", project_id)`; False → "already in progress" | `watch(...)` | the existing `stop_generation` | `project_id in self.running_tasks` |
| Insights (`start_message`) | `acquire("insights", project_id, steal=True)` (today's last-writer-wins, now across pods) | `watch(...)` | `self.stop_message(project_id)` | `project_id in self._running_tasks` |

- If spawning fails after `acquire`, the service releases the lease before
  re-raising.
- `insights.start_message` becomes `async` (it now awaits `acquire`). Its
  only caller, `routes/insights.py:115`, is already async.
- Each service gains an async `is_running_anywhere(...)`: the local dict, or
  `is_active`. The sync `is_running` stays local for internal callers
  (websockets, delegation runner, monitor), because those are about this
  pod's process.

### The routes

- **`routes/execution.py`:**
  - `/running`: the local tasks plus `active_keys("task")`, deduplicated.
  - `/{id}/status` and `/{id}/running`: `is_running_anywhere`.
  - Start guard: 409 when `is_running_anywhere` and not `force_execution`.
    With `force_execution` and a remote owner, `stop_and_wait` (as today's
    local stale-process cleanup); still held → 409 "still stopping on
    another replica, retry".
  - Stop: local → as today. Remote only → `request_stop`, return
    `{"success": true, "message": "Stop requested on the replica running
    it"}`. Neither → 404 as today.
  - Recover: a remote lease → `stop_and_wait`; still held → 409, never a
    second process. Otherwise as today.
- **`routes/tasks.py:1650`** (approve-plan auto-restart): the same
  force-path treatment as the start guard.
- **`routes/github.py`:**
  - review guard (:2108): `is_running_anywhere`;
  - cancel (:2392): local → as today; remote → `request_stop`, returning
    `{"cancelled": true, "requested": true}`.
- **`routes/insights.py`:** stop cancels locally, or sets `request_stop`
  (the lease row may belong to another pod).
- **`routes/changelog.py`:** the guard uses `is_running_anywhere`.

### One replica

- Every run takes one INSERT and one DELETE, plus one tiny UPDATE per
  heartbeat.
- Behaviour is unchanged: local stops still act immediately, and a local run
  holds its own lease.
- On SQLite (dev), the same code runs against the local database.

## Alternatives rejected

- **`job_states` / `JobStateStore`:** hard-wired to `kind="plan"` and one
  global admission cap (intent).
- **Forwarding a stop over HTTP to the owner's pod IP:** rejected in the
  intent.
- **Adding lease calls at each of the ~8 `running_tasks` removal sites and
  the failover respawns:** the `alive()` poll covers them all from one place,
  and a missed site would leak a lease.
- **A per-pod "session affinity" for the portal:** it does not help calls
  from MCP remote loopback or CFactory, and it hides the problem.
- **Making the sync `is_running` async everywhere:** it ripples into
  websockets and the monitor, which rightly care only about the local
  process.

## Risks

- **Exit-to-release latency:** up to 1 s after a run leaves the local dict,
  a start on another pod still sees it as running. Stop latency across pods
  is up to one heartbeat (15 s), accepted in the intent.
- **A pod killed without cleanup:** its runs show as running until
  `lease_until` passes (at most 60 s), then as not running. The portal's
  existing stuck detection (disk says in progress, not running) then offers
  recover. That is today's single-pod behaviour after a crash, bounded.
- **An insights steal:** the old owner cancels on its next heartbeat, so a
  superseded reply can still stream for up to 15 s on the old pod (its
  events are pod-local; see #804).
- **A long database outage:** runs keep going, and ERRORs are logged. A
  duplicate is possible only after the TTL passes, and it is logged.
- **Stop on a remote run reports success before the kill happens:** the
  response says "requested", and the owner's own status events follow.

## Verification

- **Helper unit tests** (SQLite, `apps/web-server/tests/test_run_leases.py`,
  two owners by patching `OWNER`):
  - exclusive acquire;
  - acquiring an expired lease;
  - steal;
  - release only by the owner;
  - `request_stop` makes `watch` call `stop`;
  - a lost lease makes `watch` call `stop`;
  - `alive()` going false releases;
  - a DB error in the heartbeat does not call `stop`.
- **Route tests** with a lease held by a fake other owner:
  - `/running` and `/status` report running;
  - start returns 409;
  - stop returns "requested" and sets the flag;
  - recover refuses while held;
  - PR review start returns 409 and cancel returns "requested";
  - the changelog guard refuses.
- **A Postgres race test:** 8 concurrent `acquire`s of one key, exactly one
  wins, using `reset_schema` and the migration.
- Run the new tests on the current code first: they fail (no helper, no
  table).
- Existing suites stay green, especially the agent-service, execution-route,
  insights, changelog and PR-review tests. Watcher loops are cancelled or
  fast-forwarded in tests with small TTL and heartbeat env values.
- Gates:
  - ci.yml per-process;
  - store mode;
  - `tests/postgres` twice in a row;
  - the ratchet in CI form (ruff + mypy);
  - ruff 0.15.17.
- Docs: the two new env vars in `docs/dev/environment-reference.md`, and
  #805 removed from the `guides/shipping.md` blocker list.

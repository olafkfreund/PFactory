# Spec: Three planning components are still hardcoded English

## Facts established

- Localised components use `useTranslation('common')` with one namespace block
  each: `planEditor` (PlanEditor), `annotations` (AnnotationPanel), `approval`
  (ApprovalPanel).
- `src/shared/i18n/__tests__/planning-locale-parity.test.ts` compares key SETS
  across `en`/`fr`/`pt-BR`, but its `NAMESPACES` list covers only `planEditor`
  and `annotations` — `approval` is unguarded (no drift today: 5/5/5).
- `__tests__/i18n-mock.ts` resolves a key against the real `en` bundle and
  throws `missing en translation for '<key>'`, so a missing key fails a test.
- `PlanUploadForm.test.tsx` has 9 English-text queries; `EnrichmentPanel.test.tsx`
  has none (it asserts structure, not copy); `PipelinePanel` has no test file.

## Design

### Namespaces (one block per component, in `common.json`)

`pipelinePanel`, `enrichmentPanel`, `planUploadForm` — named after the
component so a string in the UI is greppable to its key, matching `planEditor`.

### Components

Each gains `const { t } = useTranslation('common');` and every user-facing
string becomes `t('<ns>.<key>')`, including `aria-label`s, `placeholder`s and
empty-state prose. Interpolation follows the existing style
(`{{count}}`), not string concatenation.

- `PipelinePanel`: the `KIND_META` map's `label` fields become key ids resolved
  at render (the map is module-level, so it cannot call `t` directly — it keeps
  `labelKey: 'pipelinePanel.kindFeature'` and the component resolves it).
- `EnrichmentPanel`: headings, the two adapter `aria-label`s, and both empty
  states.
- `PlanUploadForm`: labels, placeholders, buttons, helper text, `aria-label`s.

**Decided (intent Q1):** the badge labels `adr` / `doc` / `policy` /
`best-practice` / `catalog` / `template` stay as fixed identifiers. They name
the source kind the API returned; translating them would break the link
between badge and payload.

### Locales

Keys added to `en`, `fr` and `pt-BR`, with real translations in the latter two
(same register as the existing `planEditor` entries, e.g. "Critères
d'acceptation", "Critérios de aceitação").

### Guards

- `planning-locale-parity.test.ts`: `NAMESPACES` becomes
  `['planEditor', 'annotations', 'approval', 'pipelinePanel', 'enrichmentPanel',
  'planUploadForm']` — adding `approval` closes the pre-existing gap.
- `PlanUploadForm.test.tsx` adopts the `i18n-mock`, so its 9 text queries
  resolve through the real `en` bundle: a missing/misspelt key fails there.

## Alternatives rejected

- **English copied into `fr`/`pt-BR`**: passes the parity test while a French
  user still reads English — the defect wearing a key (intent constraint).
- **A new namespace file (`planning.json`)**: the three localised components
  already live in `common.json`; splitting now would leave the planning flow
  half in each.
- **Translating the badge identifiers**: see intent Q1.
- **Leaving `aria-label`s in English**: accessibility copy is user-facing.

## Risks

- Translation quality: `fr`/`pt-BR` strings are written to match the register
  of the existing entries; a native reviewer may want wording changes. Keys and
  rendering are unaffected by such edits.
- `PipelinePanel`'s module-level map changes shape (`label` → `labelKey`); any
  other consumer of that map must be checked (grep in the plan).

## Verification

- `npx vitest run src/components/planning src/shared/i18n` green, including the
  parity test with six namespaces.
- Negative control: delete one new `fr` key → the parity test fails; point one
  component at a non-existent key → the i18n-mock throws in that component's
  test.
- `grep` over the three components for residual quoted user-facing text
  (`aria-label="`, `placeholder="`, JSX text nodes) returns nothing.
- English rendering unchanged: the existing `PlanUploadForm` assertions still
  match the same words through the mock.

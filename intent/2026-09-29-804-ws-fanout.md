# Intent: events reach only the browser connected to the emitting pod

## Problem

Every WebSocket subscriber registry is per process:

| where | registry | consequence with 2 replicas |
| --- | --- | --- |
| `websockets/events.py:42,46` | `_clients`, `active_connections` | `broadcast_event` walks one pod's sockets; a browser on the other pod never hears the event |
| `websockets/logs.py:45` | `agent_service.register_log_callback` | the callback fires on the pod running the task; a viewer elsewhere gets an open socket and silence |
| `websockets/progress.py:48` | `agent_service.register_progress_callback` | same |

63 call sites emit through `events.py`'s send functions, so the gap is in those
functions, not in the callers.

The chart already says so: `charts/pfactory/values.yaml` pins
`replicaCount: 1` with the comment *"WebSocket fan-out limitation"*. Found in the
multi-replica audit for `factory-gitops#273`.

There is no `LISTEN`/`NOTIFY` anywhere in the repo today, so this introduces a
mechanism rather than extending one.

## Outcome

An event emitted on any pod reaches every subscribed browser, whichever pod its
socket landed on — for the discrete event stream, the per-task log stream and the
per-task progress stream. Cookie affinity is not a fix: it helps one browser keep
one pod, and does nothing for an event that starts on another pod.

## Affected

- `apps/web-server/server/websockets/events.py` — `broadcast_event`,
  `send_to_user`, `send_to_org` and the `emit_task_*` helpers above them.
- `apps/web-server/server/websockets/{logs,progress}.py` — and the
  `AgentService` callbacks they register against.
- A new relay component (publisher + per-pod listener) and its lifecycle in
  `server/main.py`.
- `charts/pfactory/values.yaml` — the pin comment, once this half is done. The
  pin itself cannot lift until #805 and #828 are also fixed.

## Constraints

- **Postgres `NOTIFY` payloads are capped** (8000 bytes, and the whole queue is
  bounded). A task log line can exceed that, so the log stream cannot naively
  carry its content through a notification.
- `LISTEN` needs a dedicated connection held open, not a pooled one — so this
  cannot ride the SQLAlchemy request pool.
- **A DB hiccup must not silence a local browser.** Today a pod delivers to its
  own sockets with no DB involved; that must remain true when the relay is down.
- Events must not be delivered twice to a socket on the emitting pod.
- Single-replica behaviour must be unchanged, since that is production today.
- `websockets/terminal.py` is **out of scope**: a PTY lives on one pod, so a
  terminal is inherently pod-bound (that is #805's territory, not fan-out's).

## Open questions

1. **Does the log stream go through the relay at all?** It is the highest-volume
   path and the one that does not fit in a `NOTIFY` payload. Options: notify a
   pointer and have the receiving pod read the content it already persists;
   route log sockets to the owning pod; or accept truncation. My inclination:
   notify a pointer, because the logs are already on disk and the relay then
   carries a few bytes per line instead of the line.
2. **Publish-then-deliver, or deliver-locally-and-publish?** Publishing first and
   letting every pod (including the emitter) deliver on receipt gives one code
   path and one ordering. Delivering locally first and publishing for the others
   keeps today's behaviour when the DB is down. I lean to the second — the
   constraint above says a DB hiccup must not silence a local browser — at the
   cost of two paths and a self-skip.
3. **Is Postgres the right transport**, given it is a hard dependency already, or
   should this be an interface with a Postgres implementation so a future Redis
   or NATS swap is not a rewrite? The former is smaller; the latter is one extra
   indirection. I lean to the former until a second implementation actually
   exists.

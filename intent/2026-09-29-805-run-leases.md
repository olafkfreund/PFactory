# Intent: running work is visible, guarded and stoppable from any replica

Blocks factory-gitops#273 (lifting the PFactory KEDA one-replica pin).

## Problem

Four web-server services record "what is running" only in the memory of the
pod that started it:

| Service | Per-process record | Keyed by | The running thing | Routes that depend on it |
|---|---|---|---|---|
| Agent tasks (`services/agent_service.py:55`, plus ~12 per-task dicts) | `running_tasks` | `project_id:spec_id` | a pty subprocess | start guard (409), `/running`, `/{id}/status`, `/{id}/running`, stop, recover, approve-plan restart |
| Insights (`services/insights_service.py:105`) | `_running_tasks` | `project_id` | an `asyncio.Task` | send (cancels any previous run), stop |
| Changelog (`services/changelog_service.py:75`) | `running_tasks` | `project_id` | a subprocess | generate guard; its stop and status have no route |
| PR review (`services/pr_review_service.py:171`) | `running_reviews` | `project_id:pr` | a subprocess | review guard (409), cancel |

With 2 replicas, a request can reach the pod that does not own the run:

- **Status lies.** `/running` says false, so the portal's own "stuck"
  detection (`TaskCard.tsx:141`, `useTaskDetail.ts:93`) flags a healthy task
  as stuck.
- **The duplicate-run guard does not hold.** A second start of the same task
  or review succeeds on the other pod: two agents on one spec directory.
- **Stop does nothing.** Stop, cancel and recover return 404 or "not
  running" and cannot kill the subprocess. Recover can even restart a task
  that is still running on the other pod.

There is no shared record of "running" at all. The only durable trace is a
`status` field in the task's `test_plan.json`, with no owner and no
heartbeat, so it still says `in_progress` after a crash.

**Production use today:** 2 projects. In the last 30 days: no portal task
runs, 0 PR reviews, 0 insights sessions. The MCP task tools
(`task_create_and_run`, `task_status`) do **not** use these services: they
run through `agents/tools_pkg/tools/task_control.py` and filesystem
`status.json`, so this issue does not cover them.

## Proposed outcome

- Any replica answers "is X running?" correctly.
- At most one run per key across all replicas. A second start gets the same
  answer it gets today on one pod (409, or "already running").
- Stop, cancel and recover reach the run whichever pod receives the request,
  and the owning pod kills or cancels it.
- A run whose pod died is recognisably dead: its record expires, so it shows
  as stuck and recoverable, not as running forever.
- Behaviour on one replica is unchanged.

## Affected users and systems

- The four services and their routes (`routes/execution.py`,
  `routes/tasks.py`, `routes/insights.py`, `routes/changelog.py`,
  `routes/github.py`), plus `agent_process_monitor.py`.
- The Postgres schema (a new table), with SQLite for dev and tests.
- Portal users running tasks, PR reviews, insights or changelogs.
- Out of scope:
  - live event and log fan-out across pods (#804);
  - the MCP filesystem task path;
  - the dead `stop_generation` and `get_status` in changelog and PR review,
    which have no route (noted, left alone).

## Constraints

- Reuse the proven #758 emit-lease pattern: one conditional `UPDATE/INSERT
  ... RETURNING` on the database clock, an owner string that names the pod,
  and TTL expiry, rather than inventing a mechanism.
- Do not reuse `job_states`: its rows are hard-wired to `kind="plan"` and one
  global plan-admission cap (store.py:301, `try_start`), so task runs would
  eat plan slots.
- No new pod-to-pod network path or credential unless the stop design
  requires it (see question 2).
- Lease loss must fail safe: a pod that cannot renew its lease must not keep
  claiming the run silently.

## Open questions

Resolved 2026-09-29 (approved): 1 = (a) all four services on one shared lease helper; 2 = (a) a stop_requested flag polled by the owner on each heartbeat; 3 = 60 s TTL, 15 s heartbeat, configurable.

1. **Scope:**
   - (a) all four services on one shared lease helper;
   - (b) agent tasks and PR review only (long subprocesses with a user-facing
     stop), leaving insights and changelog as they are;
   - (c) instead of fixing, refuse these four features when
     `PFACTORY_REPLICA_COUNT > 1`, like #807's device flow.

   **Recommended: (a).** One helper keyed by `(kind, key)` costs little more
   than two call sites, and insights has the same stop bug. (c) is smallest,
   but it disables the portal's core task execution whenever PFactory scales,
   which only moves the problem.
2. **How a stop reaches the owning pod:**
   - (a) a `stop_requested` flag on the lease row, which the owner's existing
     per-run monitor loop checks on each heartbeat (a few seconds);
   - (b) the receiving pod forwards the stop over HTTP to the owner's pod IP
     recorded in the lease.

   **Recommended: (a).** It needs no new network path, auth or pod IP
   bookkeeping, and it works while the owner is busy. The cost is up to one
   heartbeat interval of latency before the kill.
3. **The lease TTL and heartbeat:** a short TTL (e.g. 60 s, heartbeat every
   15 s) so a dead pod's run shows as stuck within a minute, or longer?
   **Recommended: 60 s / 15 s.** It is configurable like
   `PFACTORY_EMIT_LEASE_TTL_SECONDS`.

# Intent: Three planning components are still hardcoded English

## Problem

`CLAUDE.md` requires every user-facing string in the frontend to go through
`react-i18next`. #707 localised `PlanEditor` and `AnnotationPanel`; `ApprovalPanel`
was already done. Three components in `components/planning/` still have no
`useTranslation` at all:

| component | user-visible strings (measured) |
| --- | --- |
| `PipelinePanel.tsx` | 4 — child-kind labels (`Feature`, `Testing`, `CI/CD`) + "Acceptance criteria" |
| `EnrichmentPanel.tsx` | 15 — incl. `aria-label`s ("Adapter available/unavailable"), empty states ("No AI context was gathered for this plan."), section headings, badge labels |
| `PlanUploadForm.tsx` | 20 — field labels, `aria-label`s, placeholders, buttons ("Ingest plan", "Choose file"), helper text |

So a French or Brazilian-Portuguese user meets English in the middle of the
planning flow, and the repo's own rule is broken in the components a new plan
passes through first.

## Proposed outcome

- The three components use `useTranslation('common')` and every user-facing
  string — including `aria-label`s and placeholders — resolves from a key.
- Keys exist in all three locales (`en`, `fr`, `pt-BR`), following #707's
  layout (`<componentName>.<key>` under `common.json`).
- `PlanUploadForm.test.tsx` (9 English-string queries today) uses the existing
  `__tests__/i18n-mock.ts`, which resolves against the real `en` resource and
  throws on a missing key — so a forgotten key fails a test, not a user.
- No visible change in English: the rendered text is identical.

## Affected users and systems

- `fr` / `pt-BR` users of the planning flow; `en` users see no change.
- `apps/frontend-web/src/components/planning/{PipelinePanel,EnrichmentPanel,PlanUploadForm}.tsx`,
  the three `common.json` locale files, and
  `__tests__/PlanUploadForm.test.tsx` (+ `EnrichmentPanel.test.tsx` if it
  starts matching on text).
- Frontend only: no backend, no API, no schema.

## Constraints

- Translations must be real French / Brazilian Portuguese, not English copied
  into the other files: a key that renders English in `fr` is the same defect
  wearing a key.
- English rendering must not change (same words, same interpolation).
- `aria-label`s count as user-facing (accessibility is not exempt).

## Open questions

1. The `EnrichmentPanel` badge labels (`adr`, `doc`, `policy`, `best-practice`,
   `catalog`, `template`) mirror data values from the enrichment payload rather
   than being prose. Translate them, or keep them as fixed identifiers?
   Recommendation: keep them as-is — they name a source kind and match what the
   API returns; translating them would break the link between badge and data.

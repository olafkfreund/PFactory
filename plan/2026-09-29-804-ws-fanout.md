# Plan: relay WebSocket events between pods through Postgres

Carried over from the approved intent and spec:

- **Postgres `LISTEN`/`NOTIFY`**, no new dependency. The chart's "Redis-fan-out
  (#40)" note is stale (`#40` here is an unrelated closed issue) and gets
  rewritten.
- **Deliver locally first, then publish.** A relay failure is logged and
  swallowed: a DB hiccup must never silence a browser on the emitting pod. This
  is the constraint that rules out publish-then-deliver.
- **Self-skip by origin**, `HOSTNAME` + a process-start nonce.
- **No pointer indirection.** Log content is persisted only on the emitting pod's
  RWO volume, so a pointer is unreadable cross-pod; payloads travel whole, under
  a size guard.
- **Inert without `DATABASE_URL`** — the single-process and test paths must behave
  exactly as today.
- `websockets/terminal.py` is out of scope (a PTY is pod-bound; that is #805).

## Steps

1. **`apps/web-server/server/websockets/relay.py`** (new).
   - `_origin_id()` — `f"{os.environ.get('HOSTNAME', 'local')}:{uuid4().hex[:8]}"`,
     computed once at import.
   - `_encode(kind, data) -> str | None` — JSON-encodes
     `{"origin", "kind", "data"}`; if over `_MAX_PAYLOAD = 7900` bytes (below
     Postgres's 8000 cap, leaving room for the channel framing), truncates
     `data["content"]` or `data["chunk"]["content"]` and sets
     `data["truncated"] = True`; returns `None` if it still does not fit.
   - `async def publish(kind: str, data: dict) -> None` — no-op when the relay is
     not started; otherwise `SELECT pg_notify('pfactory_ws', $1)` on the relay's
     connection. Never raises: log a warning and return.
   - `async def start_listener(deliver: Callable[[str, dict], Awaitable[None]]) -> None`
     and `async def stop_listener() -> None` — own `asyncpg` connection from
     `DATABASE_URL` read directly (strip the `+asyncpg` dialect prefix), `LISTEN
     pfactory_ws`, dispatch to `deliver(kind, data)` for notifications whose
     `origin` differs from `_ORIGIN`, reconnect with capped backoff on loss.
     Inert (and log once at INFO) when no `DATABASE_URL` is set.
2. **`apps/web-server/server/websockets/events.py`** — split each of
   `broadcast_event`, `send_to_user`, `send_to_org` into a `_deliver_local_*`
   half and a public half that calls the local half and then
   `relay.publish(...)`. The public signatures do not change, so the 63 call
   sites and every `emit_task_*` helper are untouched.
3. **`apps/web-server/server/services/agent_service.py`** — `_emit_log` and
   `_emit_progress` gain the same shape: fire local callbacks, then publish
   (`kind` = `"task:log"` / `"task:progress"`, `data` carrying the task id and the
   model dump). The local-callback half must be callable on its own, because the
   listener calls it.
4. **A dispatch table** mapping `kind` → local delivery function, in `relay.py`
   or a small `websockets/_dispatch.py`, so `start_listener`'s `deliver` is one
   lookup rather than a chain of `if`s. It must not import `events.py` at module
   import time if that creates a cycle — import inside the function if so.
5. **`apps/web-server/server/main.py`** — start the listener in `lifespan` after
   `attach_stores_after_migrations` (so the schema is settled), and stop it on
   shutdown. Failure to start is logged, not fatal: the server must boot without
   the relay.
6. **`charts/pfactory/values.yaml`** — rewrite the two stale comments (line 6's
   "WebSocket fan-out limitation" and lines 330-333's "v1.1's Redis-fan-out
   (#40)") to say what is true after this change: the WebSocket half is relayed
   through Postgres; the pin stays at 1 pending #805, #828 and RWX storage.

## Deviations found during step 1-2

1. **The URL must not come from `engine._resolve_database_url()`** (as this plan
   first said). That helper falls back to a SQLite URL at `~/.pfactory/data.db`
   for local dev, which is right for SQLAlchemy but would hand `asyncpg.connect()`
   a URL it cannot use — and would break "inert without `DATABASE_URL`" in the
   same step. `relay.py` reads the env var directly and returns `None` when unset.
   Raised by the coder, verified here at `engine.py:35-46`.

2. **`publish` needs a lock.** It executes on the same `asyncpg` connection the
   listener holds, and an asyncpg `Connection` is not safe for concurrent
   operations: two overlapping `broadcast_event` calls raise `InterfaceError:
   another operation is in progress`, which `publish`'s own `except` swallows — so
   the symptom would be silently dropped notifications under exactly the
   concurrency the relay exists for, with 63 emit sites making overlap normal. A
   module-level `asyncio.Lock` around the single `execute` fixes it; a pool would
   be larger for no gain on a payload this small. Add a test for concurrent
   publishes to the step-7 list.

3. **Step 3's relay import must be absolute.** A relative `from ..websockets
   import relay` in `agent_service.py` is one net-new `TID252`, and the ratchet
   gates **per rule per file** — the file's ruff total stayed at 72 only because
   splitting `_emit_progress` happened to drop a `PLR0912`, which the gate does
   not offset. Changed to `from server.websockets import relay`, beside the two
   absolute imports the file already has. Per-rule parity with `origin/dev`
   verified in a worktree (TID252 7 = 7; PLR0912 4 → 3, a reduction, which the
   gate allows).

   Worth stating because it is the second time this trap has cost a round:
   comparing a file's **total** finding count says nothing about whether the
   ratchet passes.

4. **Step 6 found a third stale Redis claim, not two.** Besides the header line
   and the workspaces caveat, the `rmux` block (`values.yaml:315-316`) also
   promised "v1.1's Redis pub/sub for session visibility across pods". It is
   corrected rather than left, because leaving one of three identical false
   claims makes the other two corrections look arbitrary — and because pub/sub of
   any kind would not fix rmux: a session's FIFOs live in a pod-local `emptyDir`,
   so there is nothing to relay. That now points at #805.

## Review round 1: nine findings, none of which CI could see

PR #833 passed all 32 checks, 5277 tests and ten mutation-verified unit tests. An
independent review of the diff against this plan then found nine defects, several
reproduced against a real Postgres with `pg_terminate_backend`. Fixed in this
branch:

1. **The reconnect loop was unreachable.** The listener only awaited
   `queue.get()`, and asyncpg puts nothing there when a connection dies, so the
   backoff ran only if the *initial* connect failed. Any Postgres restart or idle
   timeout removed the pod from the fan-out permanently, in both directions,
   silently — its own browsers kept working, so nothing looked broken. Now
   `is_closed()` is checked at the top of each iteration with a 1s-bounded
   `wait_for`, so death is detected regardless of any callback.
2. **Truncation produced a payload the receiver could not rebuild.** `truncated`
   was set inside `data`, but `TaskLog` has no such field, so `TaskLog(**data)`
   raised and the oversized line was *dropped* — the exact case truncation exists
   for. The flag moved to the envelope.
3. **The nested-chunk branch was dead.** This plan said `data["chunk"]["content"]`;
   `emit_task_logs_stream` puts it at `data["payload"]["chunk"]["content"]`, so
   every oversized broadcast chunk was dropped whole. Now an explicit candidate
   list. **The wrong path came from this plan and was implemented literally.**
6. `stop_listener` was unbounded, and a cleanup failure could replace a
   cancellation and loop into a reconnect, so `await _listener_task` never
   returned. Bounded, and `contextlib.suppress(Exception)` leaves `CancelledError`
   alone.
7. `main.py`'s failure branch was unreachable (`start_listener` only
   `create_task`s) and its success log read a private attribute that is non-None
   whether or not a connection exists. Replaced with `relay.is_connected()`.
8. The startup/reconnect no-op window is now documented.
9. An unrecognised `TaskPhase` logged once *per notification*, and a payload
   decoding to a non-dict killed the listener connection. Both handled.

4. **Every agent stdout line cost a Postgres round-trip**, serialised
   process-wide under `_publish_lock`, inside the stdout reader — so consuming a
   task's output was gated on DB latency and on every other emit site in the
   process. Now a bounded outbox (`maxsize=2000`) plus one drain task: `publish`
   is `_encode` + `put_nowait`, dropping with a deduped warning when full.
   `_publish_lock` is **deleted** — one drain task serialises by construction, so
   the lock became dead weight. The outbox is created inside `start_listener`, not
   at import: an `asyncio.Queue` binds to the first loop that touches it, which
   breaks a suite that gives each test its own loop.
5. **A wedged client stalled all cross-pod delivery** and grew the inbound queue
   without bound. The inbound queue is now bounded and **drop-oldest** (a
   notification's value decays with age, and it means the termination sentinel
   always gets in rather than being the one dropped), and each `send_text` has a
   5s timeout that the existing `except` already treats as a send failure. This
   improves single-replica too, where one wedged browser previously blocked every
   other client's events.

A test I had personally mutation-verified became **vacuous** under finding 4's
change: `test_publish_failure_does_not_prevent_local_delivery` monkeypatched
`_connection` with a raising fake, but `publish` no longer touches Postgres, so
the fake was never exercised and the test passed measuring nothing. Rewired to use
a full outbox — `publish`'s only remaining failure mode. Worth recording because it
is the pattern this whole task keeps producing: a green test whose subject moved.

### What the tests missed, and why

The reviewer mutated production code and **all ten tests still passed** for: a
truncation that keeps one character (the assertion recomputed its bound from the
same constant the code uses), `_dispatch_task_log` calling `_emit_log` (an
infinite two-pod ping-pong), and deleting the reconnect loop entirely.

The structural cause: **the producer → wire → dispatch → local-delivery chain was
never exercised end to end.** Every test either called `relay.publish` directly
with a matching literal `kind`, or supplied a hand-written `deliver` that never
touched `_HANDLERS` — so nothing linked a producer's `kind` string to the dispatch
table, and findings 2 and 3 lived in that gap. There is now a real-Postgres test
where pod A calls `events.broadcast_event` and pod B runs the real
`_dispatch.dispatch`; renaming the published kind to `"ws:broadcasts"` fails it.

The lesson is not "write more mutations" — ten were written and verified. It is
that mutations chosen by the same mind that wrote the code test the paths that
mind already considered.

## Rollback

Revert the commit. `relay.py` disappears, the send functions return to their
single-process form, and the lifespan starts nothing. No schema, no migration —
`pg_notify` needs no table.

## Out of scope, to be filed separately

Task detail reads `task_logs.json` from whichever pod serves the request, on an
RWO volume, so the portal is still not correct at 2 replicas after this change.
That is a storage question (RWX, or logs in Postgres), not a fan-out one.
